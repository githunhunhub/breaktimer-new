# SPEC-0025：公开装机统计报表读取性能优化

- 状态：in-progress
- 日期：2026-11-16
- 关联：SPEC-0018 · SPEC-0022 · ADR-0023 · ADR-0029 · ADR-0031 · ADR-0032 · 代码 `server/metrics/`

## 背景 / 问题

公开看板依赖 `GET /api/public-report`。线上 `range=7d&granularity=day` 实测首字节约
13 秒，`30d` 约 51 秒，但响应体只有约 819 bytes，且当前数据非常稀疏。

根因是接口在确认 namespace 中存在任意 `h_` key 后，仍按范围内全部日期、三个日维度和
每个维度 16 个分片盲目读取 KV。即使某个日期或维度没有任何数据，也会执行完整的分片
读取。读取次数为：

```text
范围天数 × 3 × 16 + 32 个全局 key
7d  = 368
30d = 1472
90d = 4352
```

这与线上约每秒 28～29 次 KV 读取的耗时一致。现有测试还把 90 天请求至少产生 1000 个
并发 KV 读取当作预期，实际把高扇出问题固化成了测试契约。成功响应虽然声明 60 秒公开
缓存，但重复请求仍会完整执行函数，说明当前链路没有实际复用响应。

## 需求（做什么）

1. 保留空 KV 快速路径：公开接口先用一次 `kv.list({ prefix: "h_", limit: 1 })` 判断
   namespace 是否有任何指标 key；空 namespace 不执行逐日列举或草图读取。
2. namespace 非空时，按范围内每天三个实际日期前缀列举存在的 key：
   `h_act_YYYYMMDD_`、`h_new_YYYYMMDD_`、`h_ver_YYYYMMDD_`。
3. 全局统计分别列举 `h_total_` 和 `h_install_ver_` 前缀，只读取列表中实际返回的 key。
4. 公开报表不得对范围内理论存在但列表未返回的 key 调用 `kv.get`。
5. 日期与全局 key 的列举使用有上限的并发批次，不一次创建无界 KV 请求；不得永久列举
   整个 `h_` namespace 的全部历史数据。
6. 成功公开响应使用 EdgeOne Cache API 缓存最多 60 秒。缓存 key 规范化为
   `range` 和 `granularity` 两个白名单参数；命中缓存时不访问 KV。
7. 缓存只保存成功的 200 响应。参数错误、方法错误、KV 错误和其它失败不得进入公开缓存。
8. 保持现有公开响应字段、日/月粒度合并语义、HLL 口径、隐私白名单、60 秒公开
   `Cache-Control` 和通用错误响应不变。
9. 私有 `/api/report` 的鉴权、任意日期范围、JSON/CSV 输出与 `no-store` 行为不变。
10. `kv.list` 返回 `complete=false` 时必须携带 `cursor` 继续列举，直到
    `complete=true`；未完成分页不是 KV 错误，也不得因此让公开报表返回 `503`。
11. 公开报表诊断日志记录 `listPrefixCount`、`listPageCount`、`listedKeyCount`、
    `readKeyCount`、`cache`、`emptyNamespace`、结果行数与汇总计数，用于区分数据为空、
    列举异常、KV 读取失败和缓存命中；日志不得输出具体 KV key、value 或敏感请求信息。
12. EdgeOne `kv.list` 返回的 `keys` 条目按官方契约从 `key` 字段读取 key 名；不得依赖
    非官方的 `name` 字段，否则列表成功后在解码阶段抛错并让公开报表返回 `503`。

## 验收标准（可测）

- [x] **D1** 稀疏数据下，公开报表只读取 `kv.list` 返回的实际指标 key；列表中不存在的
      日期、维度和分片不产生 `kv.get`。
- [x] **D2** 90 天稀疏报表的 KV `get` 数等于实际存在的相关 key 数，不再出现上千个
      理论分片读取；KV 操作并发有明确上限。
- [x] **D3** 日期列举只使用范围内每天三个实际维度前缀，全局列举只使用 `h_total_` 与
      `h_install_ver_`；不得列举全部历史 `h_` key。
- [x] **D4** 空 KV 在 7/30/90 天与日/月六种组合下仍只执行一次 `h_` 探测，不执行草图
      `get`，并返回完整 200 全零报表。
- [x] **D5** 同一规范化查询在 60 秒内第二次请求命中 Cache API，不访问 KV，且响应体与
      首次成功响应一致。
- [x] **D6** 缓存超过 60 秒失效并重新计算；KV 失败不缓存，后续请求仍按失败语义处理。
- [x] **D7** 日/月粒度、范围汇总、版本分布、空日期补零、方法限制、参数白名单、隐私字段
      和 60 秒响应头全部保持原有测试覆盖。
- [x] **D8** `server/metrics` 的 `npm test`（90 项）与 `app/` 的 `pnpm verify` 通过。
- [ ] **D9** 部署到预览或线上环境后，`7d`、`30d`、`90d` 的公网 TTFB 明显下降；同一 URL
      在 60 秒内重复请求能够命中缓存。该线上验收需要单独授权部署后完成。
- [x] **D10** SPEC 索引、ADR 索引、架构说明、路线图和 `server/metrics/README.md` 已同步。
- [x] **D11** 非空 `kv.list` 返回分页结果时，公开报表跟随 `cursor` 读完所有页，并从后续
      页面返回的 `{ key }` 条目生成报表，不再返回 `503`。
- [x] **D12** 稀疏数据成功日志中的 `listedKeyCount` 等于实际指标 key 数，
      `readKeyCount` 等于执行 get 的 key 数；分页时 `listPageCount` 随之增加；缓存命中时
      两类读取计数均为 0。

## 非目标 / 边界

- 不修改客户端上报协议、KV key 格式、HLL 参数或写入路径。
- 本 SPEC 不引入预计算快照、定时任务、数据库或新的托管存储。定时预聚合快照作为
  独立候选记录在 SPEC-0026，当前暂缓实现。
- 不改变公开接口允许的 7/30/90 天范围、日/月粒度或响应字段。
- 不为私有 `/api/report` 增加列表查找或响应缓存。
- 不在本 SPEC 内授权部署、发布或打包。

## 设计要点（可选）

- 空 namespace 探测继续保留，因为它让首次部署和停用上报后的六种查询只执行一次 list。
- 非空 namespace 按“每天三个实际日期前缀 + 两个全局前缀”列举。7/30/90 天最多分别
  执行 23/92/272 个按范围约束的 list 调用，但只 get 实际存在的 key；与盲读 4352 个
  get 相比，稀疏数据下的扇出从“理论上限”变为“实际数据量”。
- list 调用按固定批次并发，避免 90 个请求无界堆积，同时避免每天串行等待。
- Cache API 保存带内部时间戳的响应包装，读取时再次校验 60 秒有效期；即使宿主没有按
  包装响应头自动过期，也能在函数内把过期条目当作 miss 并覆盖。
- 宿主提供 `waitUntil` 时，成功响应先返回，再把缓存写入交给后台生命周期；缓存写入失败
  仍是 best effort，不改变响应。
- 缓存命中必须在获取 KV 绑定之前判断，使短期缓存不仅减少 KV 读取，也能在 KV 暂时不可用
  时继续提供尚未过期的成功快照。
- 日志计数由实际列举、过滤和读取路径产生，不从理论分片数推算；这样线上出现空报表时，
  可直接区分 `emptyNamespace=true`、列举结果被前缀过滤、KV 读取异常和正常零值。
