# ADR-0019：装机统计采用自建匿名端点（Cloudflare Worker + D1）

- 状态：accepted
- 日期：2026-11-02
- 关联：SPEC-0018 · SPEC-0017 · SPEC-0012 · ADR-0018

## 背景

维护者需要知道应用的实际装机规模、活跃情况、升级率和安装形态分布。仓库当前只有
GitHub 资产下载量与网盘后台数据，两者都只是「分发量」，无法回答「有多少装机」「还在用吗」。

应用无账号体系，可统计的最小单位是「一份独立运行数据 + 随机 `installId`」。同时存在
几条约束：

- SPEC-0017 / ADR-0018 明确更新检查不上报遥测，本轮统计不能混进更新检查；
- 用户主要在中国大陆，境外服务可能不稳定；
- 项目没有服务器预算，维护者只有一个人；
- 上报内容必须可解释、可关闭、可审计，不能出现「偷偷采集」的观感。

## 决策

1. **口径**：统计「装机」而不是「用户」；累计/新增/活跃/留存都以 `installId` 去重计算。
2. **自建最小端点**，部署在 Cloudflare Workers，数据存 D1，运行在免费额度内；不使用第三方
   统计 SDK、Web 统计脚本或 Cookie。
3. **两种事件**：`install`（首次装机）与 `heartbeat`（每日最多一次）；时间粒度到日。
4. **默认开启**，但首次启动做一次非阻塞告知，设置页提供开关；关闭后停止请求并丢弃待发事件。
5. **字段白名单**（见 SPEC-0018）：`installId`、`day`、`firstLaunchDay`、`version`、`os`、
   `arch`、`locale`、`channel`、`event`、`schema`。服务端不落 IP、不写请求日志。
6. **端点由构建期环境变量注入**：`BREAKTIMER_METRICS_URL`。未设置时该能力完全关闭，
   因此 fork 或本地开发构建不会把数据发到维护者的端点；正式发布构建由 CI 变量提供。
7. **保留期**：`daily_active` 明细 180 天，之后只保留按日聚合；逐装机原始数据不提交 Git。
8. **更新检查保持独立**：仍只请求 GitHub 公共 Release 信息，不携带任何标识（SPEC-0017）。

## 考虑过的替代方案

- **第三方统计服务（Aptabase / PostHog / Umami）**：面板开箱即用，但引入外部 SDK、数据出境
  与额外依赖；自定义留存/版本口径受对方模型限制，且无法保证「只上报白名单字段」。
- **复用更新检查通道顺带计数**：请求更少，但只有开启自动更新检查且 24 小时内有活动的装机
  才会被计入，分辨率与口径都被污染，还会动摇 ADR-0018 的边界。
- **国内云函数（腾讯云 CloudBase / 阿里云 FC）**：大陆可达性更好，但需要实名认证，
  绑定自定义域名通常还要备案；当前量级用 Cloudflare 免费额度足够，且代码与表结构可平移。
- **只看 GitHub 下载量**：零成本，但只能得到分发量，无法得到活跃、留存和升级率。

## 后果

- 免费、无需运维服务器；需要维护一个 Worker、一个 D1 库和若干报表 SQL。
- 中国大陆网络对 `workers.dev` 的可达性不稳定，上报率会低于真实装机；数据用于看趋势和
  比例，不作为审计级数字。
- 端点 URL 是一行常量，若将来迁往国内服务，只需改构建变量与重放表结构。
- 关闭统计的用户不会被计入；默认开启 + 明确告知是覆盖面与信任之间的取舍。
- 卸载无法回传，故不提供「现存用户数」，只能用「近 30 天活跃装机」近似。
