# ADR-0012：共享 JSON 翻译资源与轻量消息格式

- 状态：accepted
- 日期：2026-10-22
- 决策者：项目维护者
- 关联：SPEC-0014

## 背景

同一批用户可见文案会出现在两个运行时：

- React 渲染设置页、休息页与无障碍文案；
- Rust 生成托盘、About 与系统通知。

如果两端各自维护翻译，文案和 key 很容易漂移。首版只需要英语和简体中文，消息格式主要是
带参数的状态文本以及分钟数的单复数；当前也没有跨语言日期、货币或富文本格式需求。

## 决策

1. `app/locales/<locale>.json` 是 React 与 Rust 共用的唯一翻译源。每个文件自带
   `locale`、原生语言名 `name`、系统语言匹配别名 `aliases` 和嵌套 `messages`。
2. `en-US` 是基准与最终回退语言。其他语言缺失 key、资源损坏、无效 locale 或系统语言
   不受支持时回退英文；`en-US` 的 schema 与 key 完整性由自动化测试保证。
3. React 用 `import.meta.glob` 自动发现 JSON；Rust 用 `include_dir` 在构建时嵌入同一目录。
4. 消息采用最小自定义格式：`{name}` 做占位符替换；值可以是带 `one` / `other` 的对象，
   `count === 1` 选择 `one`，其余选择 `other`。
5. 不引入完整 ICU MessageFormat。若未来需要复杂复数规则、日期/数字/货币格式、select、
   rich text 或 RTL，另立 ADR 评估迁移。
6. 设置使用 `language: string | null`；`null` 表示跟随系统。默认休息标题和消息仅在精确
   等于旧内置英文默认值时使用内置翻译，其他内容按用户自定义文本原样显示。

## 理由

- 共享一份 JSON 可以从结构上避免前端与后端翻译漂移，同时让新增普通 LTR 语言只需增加文件。
- 当前文案格式很窄，简单的占位符和 `one` / `other` 已覆盖实际需求，实现、测试和审阅成本都低。
- 完整 ICU 需要在 JavaScript 与 Rust 两侧引入兼容的格式化实现，并携带或依赖 CLDR 规则数据；
  在只用两种语言、只需要少量参数和分钟复数的场景下，带来的依赖、包体和行为一致性成本
  明显大于收益。
- 不引入完整 React i18n 框架，避免为了资源发现、插值和切换监听增加一套额外抽象；现有
  Provider 足以承载当前范围。

## 考虑过的替代方案

- **`react-i18next` 加 Rust 独立资源**：生态成熟，但需要维护两套资源或额外同步桥接，违背
  “添加一个翻译文件”的目标。
- **Fluent**：表达力强，适合复杂语言语法；但语法、工具链和两端运行时对当前需求过重。
- **完整 ICU MessageFormat**：能覆盖复杂格式，但需要前后端一致的消息解析与 CLDR 数据；
  本期没有使用场景。
- **按语言写 Rust/TypeScript 分支**：初期文件少，但每增加一种语言都要改代码，不可接受。

## 影响

- 需要资源 schema 校验、`en-US` 完整性检查、前后端 key/格式回归测试，防止两端对同一
  JSON 的解释不同。
- 新增翻译文件仍需要重新构建；用户不能在运行期间放入外部语言包。
- 简单复数不是完整的 CLDR 规则，不能表达 Russian、Arabic 等更复杂的复数类别或选择逻辑。
- 两种语言会增加少量前端资源与 Rust 二进制体积；资源是静态文本，增量很小。
- 精确等于旧默认英文的休息文案仍会被视为内置文案，用户无法通过内容判断区分；该限制已接受。
- 未来新增语言先按“一个文件、现有语法足够、LTR”成立；超出这些条件时需要重新评估格式与布局。
