# ADR-0031：公开报表按实际 KV key 读取并使用短期响应缓存

- 状态：已接受
- 日期：2026-11-16
- 决策者：项目作者
- 关联：SPEC-0025 · SPEC-0022 · SPEC-0018 · ADR-0023 · ADR-0029

## 背景

公开报表当前复用固定 16 分片的盲读逻辑，对范围内每一天和每个维度都读取全部理论分片。
namespace 非空但数据稀疏时，几乎所有 `kv.get` 都返回空值。线上 7 天请求读取 368 个
key、耗时约 13 秒；30 天读取 1472 个 key、耗时约 51 秒。增加批次并发只能限制单轮
扇出，不能消除大量无效读取。

公开 URL 的合法组合有限，但仅返回 60 秒缓存头没有让动态函数跳过重复执行。需要同时
解决首次计算和重复访问两个成本来源。

## 决策

1. 保留一次 `h_` 前缀空 namespace 探测。没有指标 key 时直接返回全零报表。
2. namespace 非空时，对范围内每天执行一次 `h_YYYYMMDD_` 前缀列举，一次获得当天三个
   日维度的实际 key；全局 key 分别通过 `h_total_` 和 `h_install_ver_` 列举。
3. 列举按固定大小批次并发，不使用无界 `Promise.all`，也不列举整个历史 `h_` namespace。
4. 公开报表只对列举结果中的 key 执行 `kv.get`；私有 `/api/report` 保持原有固定分片读取。
5. 将成功的公开响应包装为带内部时间戳的 Cache API 条目，缓存键规范化为合法
   `range`/`granularity` 参数，有效期 60 秒。命中时直接返回缓存，不读取 KV。
6. 只缓存 200 成功响应。非法请求、方法错误、无 KV 绑定、KV 读取失败或缓存不可用都不得
   改变原有错误与 `no-store` 语义。

## 理由

- 稀疏数据下，KV 成本应随实际存在的 key 数增长，而不是随范围的理论分片上界增长。
- 按日期前缀列举把查找限制在当前查询范围内；直接列举全部历史 `h_` key 会随项目运行时间
  持续增长，最终重新引入慢请求。
- 同一天最多 48 个日指标 key，90 天范围内最多约 92 次有界 list；相比当前最多 4352 次
  无效 get，显著减少外部 I/O。
- Cache API 能跨同一边缘节点的请求复用完整响应，适合固定查询 URL；60 秒与 KV 最终一致
  窗口及现有公开缓存语义一致。
- 内部时间戳避免依赖宿主是否严格按包装响应头淘汰缓存条目；即使条目暂时仍在，过期后也会
  作为 miss 重新计算并覆盖。

## 影响

- 公开报表多了一次空探测和按范围列举的开销，但正常稀疏场景的 get 数会大幅下降。
- 第一次请求仍需读取实际存在的 sketch；缓存主要改善 60 秒内的重复访问。
- 列表结果与随后的 get 之间可能存在 KV 最终一致窗口，沿用现有 `eventual_60s` 口径，
  不提供强一致承诺。
- 公开响应在缓存命中时可能比 KV 最多再旧 60 秒，继续符合 SPEC-0022 的公开延迟说明。
- KV key、HLL 草图、客户端协议、私有报表和部署结构均不改变。
