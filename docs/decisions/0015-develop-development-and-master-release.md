# ADR-0015：develop 日常开发与 master 发版

- 状态：accepted
- 日期：2026-10-23
- 决策者：项目维护者
- 关联：ADR-0014 · SPEC-0015

## 背景

`v0.1.0` 已作为首个正式版本发布。后续如果继续在 `master` 上直接开发，发布分支会混入
尚未准备发布的提交，也无法清楚区分日常集成与正式发版。

## 决策

1. `develop` 是长期开发分支；所有日常功能、修复、测试和文档变更先提交并推送到该分支。
2. `master` 是发版专用分支；只接收来自 `develop` 的发版合入，以及发布脚本生成的版本提交。
3. 正式发布时先确认 `develop` 工作区干净并完成验证，再把 `develop` 合入 `master`。
4. 发布命令必须在 `master` 上执行；它负责版本提交、双远程 `master` 推送和只向 GitHub
   推送发布 Tag。
5. Gitee 继续作为 GitHub 之外的代码备份，接收 `develop` 与 `master`，但不接收发布 Tag，
   也不创建正式 Release。

本 ADR 替代 ADR-0014 中“日常开发完成后直接推送 `master`”的部分；ADR-0014 关于
GitHub 为唯一发布平台、Gitee 为代码备份和 Tag 只推 GitHub 的结论保持不变。

## 理由

- 将可变开发历史与正式发布历史分开，Tag 始终从经过确认的 `master` 创建。
- 日常提交和发版合入各有稳定入口，减少误推送 Tag 或从未发布代码直接发版的概率。
- 两个远程都保留完整代码备份，不改变现有发布身份。

## 考虑过的替代方案

- **继续在 master 开发**：保持现状最简单，但无法阻止未完成提交进入发版分支。
- **每次发布临时创建 release 分支**：隔离更强，但对当前单人项目和发布频率而言流程过重。
- **只保留 develop、不维护 master**：与 GitHub Tag 必须位于 `master` 的现有流水线冲突。

## 影响

- 新设备和现有设备都需要在开发前切换到 `develop`。
- `master` 允许发布合入和发布脚本产生的版本提交，不接受其他直接提交。
- 发布前需要先合入 `develop`，再在 `master` 执行 `pnpm release <version>`。
