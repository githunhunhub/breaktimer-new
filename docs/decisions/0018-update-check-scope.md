# ADR-0018：更新检查采用「只检查不安装」和 Release 元数据

- 状态：accepted
- 日期：2026-11-02
- 关联：SPEC-0017 · SPEC-0015

## 背景

应用需要让用户知道是否有新版本。可选路径包括：

1. 只检查版本并在浏览器中打开下载页；
2. 使用 `tauri-plugin-updater` 在应用内下载并安装；
3. 完全静默自动更新。

当前发布产物是未签名的 NSIS 安装包和便携 ZIP，便携版从任意目录运行并把数据写在
`data\`，无法安全地自我替换。引入 Tauri updater 还需要 minisign 密钥、`.sig` 产物、
`latest.json` 和 CI Secret，并会改变现有发布资产清单。用户当前确认只需要「检查 + 提示 +
手动下载」，因此需要明确本轮边界和下载入口的数据来源。

## 决策

1. 本轮只做「检查 + 提示 + 打开下载页」。不下载、不执行、不安装更新文件（SPEC-0017）。
2. 更新源使用 GitHub Releases API 的 `releases/latest`，只接受稳定版 `vX.Y.Z`。
   不引入 updater 插件，不新增 `latest.json`，不改现有发布资产清单。
3. 自动检查默认启用：启动后约 30 秒检查一次，之后每 24 小时最多一次；开发构建跳过，
   手动检查始终可用。
4. 不新增托盘入口；入口为设置页 `System` 页签的 `Updates` 卡片和自动检查通知。
5. 便携版接受「退出后手动覆盖文件」的更新方式，应用不尝试自我替换；`data\` 目录必须保留。
6. 下载入口按百度网盘、夸克网盘排序；GitHub 仅用于检查版本，不作为下载入口。网盘链接由发布侧维护在
   `.github/release-downloads.json`，发布流水线将其写入 Release 正文的可见段落和隐藏 JSON
   标记；应用解析隐藏标记，缺失时显示下载链接未配置提示。当前先用空值占位，链接后续补充。
7. 同一版本只自动通知一次；休息进行中延迟通知。检查失败不得误报「已是最新」。

## 考虑过的替代方案

- **`tauri-plugin-updater` + `latest.json`**：体验最好，但需要签名密钥、更新产物和 CI Secret，
  且便携版仍不能自更新；本轮成本与风险过高，留待独立需求。
- **把网盘链接硬编码进应用**：实现最简单，但链接变化需要重新发版，云盘链接失效时无法
  只更新元数据；因此选择 Release 正文元数据。
- **把网盘链接作为独立 Release Asset**：机器可读性更好，但会改变现有资产清单和
  SPEC-0015 的验收项；Release 正文标记足够满足本轮需求。
- **新增托盘「检查更新」入口**：更显眼，但会触碰 ADR-0010 的托盘菜单稳定性约束；
  当前用户明确不需要。
- **国内镜像更新源**：可改善国内网络，但 Gitee 已停用（ADR-0017），新增镜像会引入
  新的发布与同步流程；GitHub 不可达时保留手动入口，后续另立需求。

## 后果

- 用户不会被打断式强制更新；便携版和安装版的更新步骤由各自卡片说明。
- 应用只依赖 GitHub 公共 API；未认证请求有 60 次/小时/IP 限制，因此自动检查按 24 小时
  节流，手动检查加冷却，失败时不误报。
- Release 正文成为下载入口的元数据源；维护者需要在发布前更新
  `.github/release-downloads.json`，发布后也可以直接编辑 Release 正文修正网盘链接。
- 如果未来要做应用内安装，需新增 ADR / SPEC，并重新评估签名、资产、便携版和回滚策略。
